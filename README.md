# Spatial economy

A Rust simulation of households, farms, factories, trade, and research across 22 goods and services. Runs on the GPU with Burn/CubeCL and includes a Bevy viewer.

Requires the [pinned Rust toolchain](rust-toolchain.toml) and a GPU supporting `SHADER_INT64`. The Linux viewer also needs ALSA development libraries.

## Run

```sh
cargo run --release --features viewer -- view --households 1000000 --seed 42
cargo run --release -- run --households 1000000 --days 30
cargo run --release -- run --scenario scenarios/institutions.json --days 12
```

GPU and the industrial economy are the defaults. Use `--economy agrarian` for the simpler food economy, or load a [scenario](scenarios/) with its own population and settings.

Simulation compute uses Vulkan on Windows and Linux, and Metal on macOS, preferring a high-performance GPU. On supported Vulkan devices, CubeCL's native SPIR-V compiler uses GPU buffer addresses, allowing large populations to exceed the regular wgpu 2 GiB storage binding limit. The device name includes `wgpu<spirv>` when this path is active; total VRAM must still fit the scenario.

- `--seed N`: generation seed; defaults to 42.
- `--output PATH`: save results as JSON.
- `--trajectory PATH`: record daily accounts as JSONL.
- `--checkpoint PATH` / `--restore PATH`: save or resume a simulation. Add `--checkpoint-every N` for periodic saves.

See `cargo run -- --help` for all options.

The viewer starts paused and uses native Bevy UI with a Victoria 3–inspired resource bar, navigation rail, economic ledger, regional map, and actor inspector. Click **Overview**, **Market**, **Industry**, **Population**, or **Finance**, then a graph tab to view employment, wealth, prices, stocks, wages, business activity, research, demography, housing, or credit. The 28 charts include unemployment, daily production and consumption, input use, deliveries, business cash profit, receipts and outlays, business types and industries, population occupations, loan balances, rent and taxes. Graph colors match the visible legend; seed comparisons overlay the saved run with faint lines.

Use **30 days**, **1 year**, **5 years**, or **All history** to change the period across charts. The viewer retains every daily observation in the current run; reset starts a new history. **Focus next** isolates a series and rescales its axis; **Show all** restores the full chart. Hover a chart to read a day's exact values and, when comparing seeds, same-day reference values and differences. Cash brackets are also shown over time. Flow charts show changes per day, not cumulative totals; data before the first observation is unavailable.

**Population → Occupations** shows farmers, wage workers, owners, unemployed people, dependents and other adults as percentages of all living people, with person counts in the readout. Categories never overlap: age-based dependents take priority, followed by the selected adult in each managing-owner household, subsistence farmers, paid workers, unemployed labor representatives, and other adults. Farm employees count as wage workers. The simulation selects one labor representative per household; these categories describe that model. Unemployment divides unemployed representatives by wage workers plus unemployed representatives and excludes the other categories. Labor and occupation charts become available after the first simulated day.

**Industry → Profits / Accounts** shows cash-basis profit before owner payouts: actual sales receipts and collected rent minus cash outlays, including wages, inputs, rent and construction purchases. It excludes loan funding and debt service, and does not apply depreciation or inventory valuation. Negative profits remain visible below zero. Individual firm inspection includes daily receipts, outlays and cash profit. These observations are included in JSON output and checkpoints. Scroll over the ledger or inspector to read longer sections.

The top bar shows the date, season, and temperature, with **Resume/Pause**, **+1 day**, and three speed buttons (0.5 days/s, 2 days/s, maximum). **Compare seed** saves the current history and runs the next seed to the same day; **Reset run** restores the launch scenario. Click **Household**, **Firm**, **Next actor**, or a firm marker on the map to inspect its accounts. Household inspection includes wood and coal stocks, heat supplied, and unmet heating needs. Sound and flash controls are in the footer.

Keyboard shortcuts remain available: **Space** runs/pauses, **N** steps one day, **R** resets, **1/2/3** change speed, **G** cycles graphs across menus, **C** compares the next seed, **H/F/Tab** inspect actors, and **M/V** toggle sound/flashes. Run `cargo run --features viewer -- view-check --households 100` for the GPU UI check: it clicks the native controls, firm markers, and graph menus, checks that buttons fit a 1280×800 window, and writes screenshots to the system temporary directory. On macOS, keep the session unlocked for window captures; capture failures are reported separately and still make the check fail.

## Model

- Each simulation step advances one calendar day. Day 0 is 1 January, year 1; years have 365 days with no leap day. Spring runs March–May, summer June–August, autumn September–November, and winter December–February. A single deterministic temperature applies across the map, repeating annually from −5°C in January to 23°C in early July. Daily observations and actor inspections include the date, season, temperature, and heating demand. The default harvest window is 28 September–27 October.
- Below 10°C, each living person needs one heat unit for every 5°C of cold, rounded up. One wood supplies one heat unit and one coal supplies two; households buy either fuel as substitutes, counting both stored fuel and pending deliveries toward their heating reserve. They secure today's bread before buying heating fuel. Fuel burns at the daily close and remains included in goods conservation. Unmet heating accumulates cold exposure for each person; fully heated or warm days reduce exposure by the configured daily recovery. Cold deaths have a separate cause and graph series. `demography.mortality.cold_daily_ppm_at_seven_days` and `cold_vulnerability_per_mille` configure the estimated mortality response; the default risk is 1,000 parts per million per day after seven unheated days for the reference adult, rising with exposure duration.
- Subsistence farmers grow their own food. Wage workers start employed by capitalist-owned farms, factories, or distributors and buy food.
- Grain, flax, cotton, and dye farms cultivate during the 211 days preceding harvest and release finished crops only within the harvest window. The default growing season is 1 March–27 September; farms rest after harvest until the next growing season. Completed commercial crop work accumulates until harvest, with yield scaled by 365 divided by the growing days to preserve annual production capacity. Household cultivation works toward its configured annual yield per plot. `household_production.harvest_start` and `harvest_days` also control commercial harvests; windows can cross New Year. Shorter gaps between harvest windows shorten the growing period accordingly.
- Generated industrial recipes produce 10 units per 20 labor minutes. With the default growing season, commercial crop cultivation uses about 1.16 labor minutes per harvested unit; household cultivation uses 10. Commercial milling and baking each need one fifteenth of the household labor. The industrial wage is 12 cash units per minute, preserving 240 cash units per production batch; distributors use five-minute shifts at the same rate. Explicit scenario recipes and wages remain configurable.
- In industrial economies without explicit property regions, completed grain-farm expansions consolidate nearby subsistence plots when the farm uses less cultivation labor per unit and its annual output per worker exceeds the household yield per plot. Farms absorb whole local grants covering the household harvest their added annual output can replace, ordered by distance and then actor order. Displaced households lose unharvested crop work and stored grain, retain other food and cash, and can seek wage employment. Stored grain is also lost when property development displaces a household. Consolidated plots remain with the commercial farm and receive the same scale bonuses as developed property. Expansion still requires demand, funding, materials, construction labor, and an owner who wants to grow.
- Firms produce goods using labor and inputs. Natural resources constrain production sites; deliveries take at least one day.
- Clothes use cloth and linen. Luxury clothes use clothes and dye; luxury furniture uses furniture and glass. Households consume clothes every 40 days and furniture every 60 days, with the same intervals for luxury versions. Luxury buyers need their food buffer covered and the regular version owned or on its way. They spend only savings above 30 days of food and rent, or the food coverage plus delivery window if longer. Generated starting supply assumes luxury demand from 10% of households; actual purchases depend on their finances and supplies.
- Freight defaults to animal transport at `shipment_speed`. Generated industrial economies use slower animals and include railway companies with planned tracks. Steam engines and rail technology are available immediately; railway operation has no research requirement. Locomotive factories use steel, tools, and labor.
- Railway companies build one planned segment per day when their delivered materials cover its construction cost. Each opening they first pay upkeep in coal, steel, and locomotives for existing track. Missing upkeep suspends that company's tracks until supplies recover. New track costs more of all three goods than maintenance. Companies buy replenishment through the paid market, so funds, supply, and delivery delays constrain expansion.
- The `railway` configuration supplies `companies` (firm identity, `freight_rate`, `access_fee`, and optional `sharing`) and bidirectional `segments` (company identity, `from`, `to`). Endpoints are stations; only identical endpoints connect, and crossings without a shared endpoint do not connect. Initial construction materials scale by distance rounded up to `length_unit`. Defaults are 20 coal, 40 steel, and 5 locomotives for construction, then 2 coal, 1 steel, and 1 locomotive per operating day. Networks support up to 256 stations.
- Track access defaults to `"sharing": "Shared"`. Set an operator to `"Private"` to restrict its tracks to its own company and carriers listed in `sharing_agreements`, for example `[{"owner": 12, "carrier": 11}]`. Agreements are directional: this allows carrier 11 onto operator 12's tracks. Shared-track journeys pay the owner's configured access fee; sites belonging to the same company remain exempt.
- Configure a firm siding through `connections`, for example `[{"firm": 10, "company": 11, "station": {"x": 0, "y": 0}}]`. This appends a planned segment from the firm's location to an existing network station. The operator must construct and maintain it using the same materials and regional capacity rules as other tracks. Once built, the firm has direct station access at its own site. Connections survive checkpoints without duplicating tracks. Generated industrial scenarios also plan sidings for firms with at least 20 worker slots, within the 256-station network limit.
- Maintained railways produce `units_per_level` rail units per region each day (default 100); unused units expire. Regions follow the property map, or a grid of `length_unit` squares when no property map exists. Track follows an x-then-y path between stations. Moving one good five regions away consumes one unit in each of the five entered regions; the departure region is excluded, and a journey within one region uses one unit. Splitting track into extra segments does not create extra charges. Every traversed region must supply its units atomically; surplus capacity elsewhere cannot cover a bottleneck.
- Regional demand drives capacity expansion when the owner prefers expansion. Each added level consumes construction coal, steel, and locomotives and adds ongoing maintenance; missing materials must be purchased and delivered before expansion completes. Demand persists across days while materials are acquired. Multiple companies may build tracks in the same region, including parallel tracks between the same stations. Each company produces and expands its own regional supply; another operator can carry a shipment when the preferred carrier is full. Foreign operators' stocks remain separate, while sites of the same company avoid access fees.
- Shipments use the nearest departure and arrival stations, with animal transport for access to those stations. The GPU finds a maintained route for each carrier, preferring its own connected tracks before using foreign rails, even when a foreign shortcut is shorter. Among funded routes with capacity, dispatch prefers less foreign track use, then lower fees and delivery time; it uses trains when they arrive sooner than direct animal transport. Trains default to eight times animal speed. Disconnected tracks, insufficient rail capacity, or a sender unable to pay for rail use animal transport immediately. The sender pays the originating carrier a freight charge per regional rail unit plus access fees, and that carrier pays each foreign track owner. Sites belonging to the same company share tracks without a foreign access fee. Deliveries already dispatched keep their arrival date if a line later closes. The firm inspector shows rail construction, service status, daily capacity, available units, and receipts. Run `cargo run --release -- run --scenario scenarios/railway.json --days 14` for a two-company example.
- Freight settlement runs in GPU passes after goods trades. Every accepted shipment evaluates its carrier choices independently. Regional capacity and sender freight budgets use exact prefix sums in deterministic seller/buyer order. Only contested resources emit claims for GPU sorting and arbitration; a shipment books only when every resource approves it. Unsuccessful bookings get one retry against remaining capacity and alternative carriers, then keep animal transport. Only committed bookings consume capacity or create payments. Operator receipts and sender charges use checked 64-bit atomic reductions followed by one account update per actor. Freight uses the sender's cash available before the goods market, capped by its remaining cash after purchases; receipts from that market become available for freight in the next market. Freight settlement is limited to two GPU waves per market. The host sizes reusable claim storage from actual contested demand; it does not settle shipments. Cross-resource contention can leave rail capacity unused when the retry limit is reached.
- Births, deaths, migration, business entry, and closures change the economy over time.
- Distributors operate from warehouse buildings (the `Store` property use) and pay daily firm rent, including while idle or under construction. With property regions enabled, a warehouse occupies plots and must finish construction before trading. Distributors liquidate after 30 consecutive days without sales that cover replacement stock, staffed shifts, and rent, even when they still have cash. This lets competition from expanding, more efficient firms drive unsuccessful shops out of business; profitable small shops can remain open. Construction is exempt from the sales test. Liquidation distributes remaining assets through the existing ownership system and leaves the building on its plot. Closed firms no longer count toward the distributor total.
- Entrepreneurial interest is a persistent seeded trait: 8% of households are interested by default, including small businesses. Interested households review local business opportunities monthly, then need savings, construction materials, and operating funds to open a firm. They estimate margins from nearby prices and available inputs; they do not know other firms' order books or prospective customers' bank balances, and sales are not guaranteed. Set `"entrepreneurship": { "interested_per_mille": 80 }` to change this modeling assumption (0 disables entry, 1000 makes every household interested).
- Generated industrial households start with unequal liquid savings: about 60% have 1.75–7 days of starting food and rent expenses, 30% have 7–28 days, and 10% have 28–112 days. This is a modeling distribution, separate from initial food inventories and ownership of land or firms. `"household_liquidity": "PaycheckToPaycheck"` uses `household_cash` as the one-week reference; omitting the setting preserves uniform balances, and explicit population cash balances are used exactly.
- Generated crop farms start with a year of forecast crop demand so stored harvests supply the economy before its first growing season. Other generated industrial producers start with two days of finished goods so replenishment provides paid work early. `"producer_buffer_days": 2` controls those stocks separately from household food and production inputs; omitting it retains the scenario's existing `buffer_days` behavior. Setting either stock buffer to zero also disables the initial crop reserve. Explicit populations retain their supplied inventories.
- Rent goes to household-owned housing firms. A housing firm has zero workers and produces `output_ticks` housing units per developed plot each day. It buys construction services for maintenance: `input_ticks` per plot covers 30 days. Existing buildings start with 30 days of maintenance coverage; without maintenance, housing supply stops. Housing services expire daily, and households without an available unit become homeless. Subsistence households with land remain exempt from rent.
- Housing firms receive household and business rent in spendable cash. Households pay after buying bread and keep their cash when their food buffer, including deliveries, is short. Ordinary firms pay after wages and retain the existing 30-day arrears grace period. Unpaid balances carry forward. Housing firms do not charge themselves rent. Tenants use the nearest rental building within their property region, or across the map when regions are absent; migration updates this assignment. Equally distant buildings share assignments deterministically. Generated rental buildings house landless households in eight units per plot when no property regions are configured, with ownership shares and no extra starting money. Subsistence households' own homes do not count toward rental capacity. Explicit populations can supply `Housing` firms with `capacity: 0` and a technique with `labor_minutes: 0`.
- Owners can pay themselves through the existing ownership distributions (`distribution_rate`). Housing firms first reserve maintenance funds and the cost of any construction project. Only owners whose expansion preference is `Expand` save toward and commission the next project when local rental demand reaches 95% of capacity, allowing a small vacancy buffer. Owners with a `Maintain` preference keep their current capacity even when housing is full and construction is affordable. New housing uses paid construction services and deliveries; property regions additionally require land and the regional owner's authorization. One completed plot adds the building's configured number of housing units.
- Expansion preferences are persistent and separate from interest in starting a business. By default, 8% of small-business owners and 60% of industrial owners seek expansion. Firms with fewer than 20 worker slots count as small businesses; larger employers count as industrial. Landlords use housing units instead of worker slots for this classification, so businesses operating at least 20 homes use the industrial expansion rate while still employing no workers. Set `"expansion": { "small_business_per_mille": 80, "industrial_per_mille": 600 }` to change these modeling assumptions. Owners who prefer to maintain their business can still receive payouts; cash alone does not trigger expansion.
- Scenario files can set `"rent": { "household_daily": 1, "firm_daily": 10 }`; these are also the generated industrial defaults. Omitting rent disables collection. The viewer shows rent paid, arrears, and housing firms' units and rental income. Checkpoints use format 18 and require regeneration from older formats. Legacy inventory arrays with 3, 16, 17, 18, 19, or 20 goods remain readable in scenarios, and `"Coats"` is accepted as the old name for `"Clothes"`.
- The optional `property` configuration partitions the map into nonoverlapping rectangular regions with fixed space and a landowner household. Housing, commercial farms, factories, and reserved construction sites share that space. Existing sites start with one plot; landless households served by configured housing firms share those buildings instead. `buildings` can override each site's footprint. Natural-good firms use farms; manufactured-good firms, including builders, use factories; housing firms use housing plots. Buildings remain on their original land after household migration or business closure.
- Landowners commission `orders` for their own household or firms using actor identities (`landowner`, `site`), `space`, `work`, and `development` (`NewBuilding` or `Extension`). New firms cannot produce until completion; extensions add the site’s existing workers per plot, or housing units per plot for rental buildings. Projects move through Requested → Building → Completed, reserving space in actor order. Unavailable space leaves requests pending; absent materials, workers, funds, or deliveries stall construction. Abandoned projects release reservations at the next opening. With property enabled, entrepreneurial entry and automatic expansion require the regional landowner and purchase 20 construction work units per added space.
- `Construction` firms hire labor and consume wood and tools using ordinary production recipes. `MechanizedConstruction` is available through mechanization research. Projects buy their output through the existing paid market and delivery system, consuming it as construction work. Subsistence households keep their plots only when their entire grant fits in the space left after buildings and reservations; otherwise they lose their plots, unharvested crop work, and stored grain and can seek wage employment. Allocation is deterministic and regional; other stored food is preserved. Migration relinquishes subsistence plots. Run `cargo run --release -- run --scenario scenarios/property.json --days 14` for a two-region example with housing, farm, and factory projects. Run output includes regional property totals; actor inspection shows land and project status. Omitting `property` retains owner-built construction for ordinary firms; housing developments still purchase construction services.
- Transactions use exact integer accounting. Daily audits check cash and goods conservation; faults restore the last audited state.
- Household food searches examine up to 128 suppliers per nearby spatial cell and choose among the first eight qualifying offers. Large cells use a deterministic rotating sample spread across their suppliers; small cells are searched completely. The buyer, day, and matching round determine the sample. Households retain local price and delivery preferences and retry over four matching rounds. A household can miss an available seller in a large market, so trajectories differ from versions with exhaustive scarcity searches while remaining reproducible for the same seed and settings.

## Test and benchmark

```sh
cargo gpu-fast
cargo gpu-full
cargo gpu-extended
cargo run --release -- benchmark --sizes 100000,1000000 --seed 42 --warmup 0 --days 1000 --output /tmp/benchmark.json
```

All test aliases use the GPU. `gpu-fast` runs 11 smoke tests; `gpu-full` runs the core regression suite, including the viewer unit tests. `gpu-extended` runs the additional scenario checks marked with an explicit ignore reason, excluding profiling benchmarks. Tests run serially to avoid GPU contention. Unit and integration tests share one library test binary and a cached GPU device; memory-budget tests use a separate binary. Add integration modules to `tests/integration.rs`; automatic test discovery is disabled. Run a single module with, for example, `cargo test --lib tests::railway`.

Check shader access across the 2 GiB boundary with `cargo test --locked --test gpu gpu_buffer_larger_than_two_gib_preserves_distant_writes -- --ignored --nocapture`. This allocates a 3.46 GB GPU buffer and requires sufficient GPU memory.

The core regression runtime budget is two minutes, excluding compilation. The extended scenarios have no two-minute limit. Measure the core suite and fail if it exceeds the budget:

```sh
cargo test --locked --features viewer --lib --tests --no-run --message-format=json > /tmp/bad-econ-tests.jsonl
python3 scripts/measure-gpu-tests.py /tmp/bad-econ-tests.jsonl /tmp/bad-econ-test-timings
```

Parallel scan, sorting, and copy tests exercise the minimum and maximum workgroup sizes. Scenario tests use a common workgroup; dedicated replay and sort-cache tests also cover the intermediate sizes. Long overlapping replays are consolidated, and lifecycle fixtures start near the transition being checked. Benchmarks report daily phase timings, memory use, and final state hashes.

Measure initialization and the first simulated days, including GPU compilation on first use:

```sh
cargo run --release --example startup_throughput -- --sizes 1000000 --days 3 --output /tmp/startup.json
```

This reports scenario generation, device setup, simulation initialization, and each day's phase timings separately, plus a final state hash. Use a separate process for each size when comparing startup; later sizes in the same process can reuse compiled kernels. GPU driver caches can also make subsequent launches faster. Input and consumer markets share compiled kernels across goods; grain and household bread retain dedicated kernels.

To enforce a strict daily latency budget after warming the complete measured trajectory:

```sh
cargo run --release --example gpu_throughput -- --sizes 1000000 --start-day 0 --warmup 2 --days 28 --max-day-ms 250 --output /tmp/throughput.json
```

This checks that the warmup and measured runs reach identical state hashes, records the slowest day, and saves the report before failing if any measured simulation step takes 250 ms or longer. Startup and reporting time are excluded from individual step timings.

Use the same seed, population, and `--start-day` for seasonal comparisons. Day 0 is 1 January, year 1, so `--start-day 0` measures winter conditions; `--start-day 120` starts in the warm growing season. With `--start-day 268 --warmup 2`, the measured run begins on harvest day 270. The preflight warms the full measured trajectory before timing it. Compare final state hashes only between repeated runs of the same simulation version; changes to the economic model can change those hashes.

Use the GPU timestamp profiler to attribute time to individual kernels:

```sh
cargo run --release -- benchmark --sizes 1000000 --seed 42 --warmup 2 --days 10 --kernel-profile /tmp/economy-kernels.log --output /tmp/economy-profile.json
```

Profiling records kernel specializations and dispatch sizes, and bypasses recorded sort graphs so their kernels can be timed. Profiling changes submission and synchronization overhead; measure overall throughput separately with `--kernel-profile` omitted, and run benchmarks without concurrent GPU tests. Payroll settles funded batches cooperatively, with ordered handling when escrow is insufficient. Rail infrastructure uses a workgroup per company, parallel regional capacity updates, and deterministic material allocation in region order. Freight reservations, capacity consumption, and inter-company payments use parallel GPU passes; deterministic arbitration resolves oversubscribed resources without a serial freight dispatcher.
